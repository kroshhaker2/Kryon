# Нативный ворлдген Kryon — контекст для второго чата

Цель владельца проекта — ускорить генерацию новых чанков. Целевая схема: Paper запрашивает чанк, Rust генерирует его данные, Paper использует их в памяти. Rust также должен записывать чанки в файлы мира `.mca`. Это цель, а не описание работающей реализации.

## Что уже есть

- `native/Cargo.toml`: Rust 2024, библиотека `kryon_native`, форматы `cdylib` и `rlib`, зависимостей нет.
- `native/src/lib.rs`: подключает `worldgen`, экспортирует `kryon_native_version`, а также создание, генерацию и уничтожение generator handle.
- `paper-server/src/main/java/io/papermc/paper/kryon/KryonNative.java`: мост через Java FFM, загружает `native/target/release/libkryon_native.so` относительно рабочего каталога процесса. По подтверждению владельца, вызов версии с сервера работает.
- `NativeChunkGenerator.java` в том же пакете наследует `ChunkGenerator`. В `buildTerrain` есть вызов `KryonNative.generateChunk`; в `ServerLevel` подстановка адаптера не реализована. Проверен на сервере только вызов версии, не генерация.
- Java `KryonNative.createGenerator` собирает все `BlockState` из `BuiltInRegistries.BLOCK` и передаёт Rust таблицу `global state ID → каноническое имя с properties`. Rust читает и хранит её в `BlockStateRegistry`. `WorldGenerator::generate_chunk` пока не реализован.
- `native/src/worldgen/dimension.rs` описывает все 16 компонентов `DimensionType` Minecraft 26.3, включая holder sets. Java передаёт полное JSON-представление через `DimensionType.DIRECT_CODEC`; Rust разбирает простые поля, сохраняет UTF-8 bytes в `DimensionType.json`, а сложные поля пока заполняет заглушками. Конфигурация генерации рельефа — отдельные данные, не часть `DimensionType`.
- `native/src/worldgen/chunk.rs` содержит модель сабчанка и `write_block_states`: сериализация уже подготовленной палитры и упакованных слов для `section.getStates().read()`. Три режима (однородный, локальная палитра, глобальные ID) проверены на уровне байтов Rust, чтение в Paper не проверено.

## Какую интеграцию хочет владелец

- Заменить генератор измерения целиком через Java-адаптер, а не патчить `NoiseBasedChunkGenerator` или включать плоский тип мира. Точка подключения: `ServerLevel` передаёт генератор в `ServerChunkCache`.
- Paper читает датапаки. На мир предлагается создавать один Rust-генератор с seed, настройками и нужными данными реестров. На запрос передавать дескриптор, координаты и только тот контекст стадии, которого нет в Rust. Не переносить `Blender`, `RandomState`, `StructureManager`, `BiomeManager` и другие Java-объекты один к одному.
- У Paper несколько стадий: биомы нужны до `buildTerrain`; `buildTerrain` отвечает за рельеф, а не за весь жизненный цикл чанка. Зависимости от соседей учитывать на соответствующей стадии.
- Rust выбирает и формирует блоки. Для рельефа граница передачи — упакованные состояния блоков сабчанков снизу вверх. Java загружает их в существующий `ChunkAccess`, сохраняя биомы, пересчитывает счётчики и обеспечивает корректные карты высот. Карта высот вместо блоков не подходит.

## Открытый вопрос ABI

Для результата переменного размера Rust владеет байтами, Java получает адрес и длину, читает их и вызывает отдельную функцию освобождения. Создание и уничтожение генератора — отдельные операции. Java-обёртка ABI добавлена, но `NativeChunkGenerator` и `ServerLevel` ещё не используют generator handle.

## Сохранение и проверка
- В `rng.rs` инициализация `Xoroshiro::new` и `mix_stafford13` используют арифметику по модулю 2⁶⁴ и множители из Minecraft. На пяти сидах сверены обе части начального состояния с включёнными проверками переполнения; методы `next_*` отдельно не реализовывались.
- В `run/libraries/kryon/native/linux-x86_64/libkryon_native.so` установлена относительная символьная ссылка на `native/target/release/libkryon_native.so`. Проверено, что оба пути указывают на один файл.
- По следующему логу выполнение дошло до Rust `generate_terrain`: `native/src/worldgen.rs:58` ищет `"stone"` без пространства имён в `ids_by_name` и паникует. Для камня нужен `"minecraft:stone"`. После исправления запуск не проверен.
- По логу запуска 25 ноября: в чанке `(2, 5)` Overworld на `STRUCTURE_STARTS` поиск места для разрушенного портала получил `null` вместо `NoiseColumn`. Для этого чанка сбой произошёл до `buildTerrain`. Проверить реализацию `getBaseColumn` активного генератора; исправление запуском не подтверждено.
- Сохранение — отдельная операция: Paper передаёт снимок актуального чанка, включая изменения после генерации. Для каждого region-файла нужен один писатель. Проверка: поставить блок, сохранить мир, перезапустить сервер и увидеть и слой, и добавленный блок без повторной генерации.
- Ускорение пока не измерялось. Сравнивать реализации на одинаковой нагрузке согласно `CONTRIBUTING.md`.

Перед правками учитывать корневые `AGENTS.md` и `CONTRIBUTING.md`. Обновлять этот файл по мере принятых решений и проверенных изменений; незавершённые этапы не отмечать как реализованные.
